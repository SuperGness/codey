# 范围与防护尺度

把工作量花在用户要求的结果上。本节只约束修法和防护加到多大，不限制发现：本项目实际可达的缺陷再罕见也要报告或修复。

- 校验放在真实边界：网络与跨进程输入、第三方数据或插件、多用户共享内容、已发布版本留下的数据。同一程序内部的调用信任类型和既有不变量，不为构造不出的状态写守卫。
- 不用吞错、静默回退、宽泛默认值或层层判空掩盖不该出现的状态；该失败时带着能定位问题的信息失败。
- 兼容层、迁移、版本号、开关和包装层只为已发布且确有存量的版本或数据而建；内部重构直接改到位，不保留旧路径或别名。
- 哈希、校验和与指纹只在能省掉更昂贵的操作且结果会改变下一步时使用。
- 冷门编码、符号链接竞态、毫秒级时序等情况，只在经由本项目的文档示例、公开接口或真实数据可达时处理；可达即可，不要求先复现。
- 检查对应尚未确认的具体风险：从未运行过的代码先跑一次最小实测；改动共享接口或格式时覆盖它的使用方；未改动且已通过的部分不重跑。
- 几种做法都合理时选一种并说明取舍；只有分歧大或难以回退时才提问。不挡路的细节记下后继续推进。
- 审查结论要能通过：指出问题时给出触发路径；没有问题就直接说正确，不为交差凑问题。
- 交付内容只写最终结果；限制和已知问题集中写在一处，不在每段附带免责声明。

用户指令或项目文档明确要求的安全、迁移、校验与审查优先于本节，那是任务本身；项目流程写得更具体时，以项目流程为准。
